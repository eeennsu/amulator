# amulator 학습 사이트 설계

- 날짜: 2026-10-19
- 상태: grilling(2026-10-19)으로 정한 방향에 빌더 점검을 반영했다. 빌더 질문 2건(DS README·배포 순서, 접기 컴포넌트)은 사용자 결정이다
- 기존 설계: [2026-10-19-amulator-design.md](2026-10-19-amulator-design.md). 이 문서는 기존 설계의 1장 "완성된 모습", 2장 반목표 한 줄, 4.2절의 `docs/learn` 줄, 5장 M2 이후 로드맵, 6장 학습 트랙, 7장 성공 기준을 대신한다. 3장 제약(REA 대상 한정, 라이선스 포함), 4.1절 런타임(브리지 보안, worker 루프, SharedArrayBuffer 미사용)은 그대로 따른다.

## 1. 의도

M1(bare-metal 그림판과 MCP 조작)까지 만든 뒤 학습 방식을 바꾼다.

- **바꾸는 이유.** 기존 설계에서는 사용자가 읽기 가이드를 따라 코드를 읽고 학습 노트를 직접 썼다. 사용자는 노트 쓰기가 부담스럽다고 했다. 가이드의 질문도 RISC-V 사양과 QEMU 내부를 이미 안다는 전제여서, 처음 보는 사람이 답하기 어려웠다. (사용자 판단)
- **새 방향.** 에뮬레이터를 교재로 삼아 원리를 인터랙티브하게 배우는 학습 사이트를 만든다. 사용자는 레포 노트 대신 이 사이트로 공부한다. (사용자 결정)
- **대상 독자.** 사용자 자신과 공개 방문자다. (사용자 결정) 독자 수준은 저수준 지식이 없는 웹·앱 개발자로 잡는다. 사용자가 그 수준이라는 점에서 정했다. (설계자 판단)
- **배움의 목표 수준.** 큰 그림을 자기 말로 설명할 수 있는 정도다. 예를 들어 "CPU는 명령어를 하나씩 꺼내 실행한다", "장치는 특정 메모리 주소다", "화면은 메모리 덩어리를 canvas에 그린 것이다"를 이해하고, 진짜 안드로이드 에뮬레이터가 같은 일을 어떻게 하는지 비교할 수 있으면 된다. 사양의 세부(예: mret 뒤 MPIE 값)는 다루지 않는다. (설계자 판단)
- **포트폴리오 목표는 그대로다.** "AI에 관심이 많은 RN 개발자"로 보이는 것이 목표다. 학습 사이트는 웹 프런트엔드 역량을 보여 주고, MCP 플러그인과 7장 재생은 AI 측면을 보여 준다.

## 2. 목표, 비목표, 반목표

### 목표

- 챕터 8개짜리 학습 사이트 v1을 공개한다. (사용자 결정)

  | # | 챕터 | 다루는 것 |
  |---|---|---|
  | 0 | 에뮬레이터란 | 큰 그림. 진짜 안드로이드 에뮬레이터와 이 에뮬레이터의 전체 구조 |
  | 1 | 부팅 | 프로그램(ELF)을 메모리에 올리고 시작 주소에서 실행을 시작하기 |
  | 2 | CPU | 명령어를 꺼내 해석하고 실행하기, 트랩 |
  | 3 | 장치 | 메모리 주소로 장치에 말 걸기(MMIO), UART와 타이머 |
  | 4 | 화면 | 프레임버퍼 메모리가 canvas가 되기까지 |
  | 5 | 입력 | 포인터 이벤트가 터치 레지스터에 들어가기까지 |
  | 6 | 스냅샷 | 상태를 저장하고 복원하기. 안드로이드의 퀵부트와 비교 |
  | 7 | 바깥에서 조작하기 | 안드로이드의 adb·콘솔과 이 에뮬레이터의 브리지·MCP 비교, Claude 조작 기록 재생 |

- 챕터마다 같은 구성을 쓴다. (사용자 결정)
  1. 설명 글. 중간중간 실제 에뮬레이터에 연결된 위젯이 들어간다.
  2. "직접 해 보기". 이미 있는 프로그램(hello, clock, 그림판)을 단계 실행하고, 레지스터와 메모리 값을 보고 바꾸고, 화면을 탭한다.
  3. 확인 질문. 독자가 답을 떠올린 뒤 펼쳐서 볼 수 있다.
  4. "진짜 안드로이드 에뮬레이터는" 상자. 기본으로 접혀 있다. AOSP 소스 링크와 REA 분석 요약이 들어간다. 디컴파일 원문은 싣지 않는다.
- Claude 플러그인(MCP)은 로컬 전용으로 그대로 둔다. 7장에서는 Claude가 그림판에 그린 tap·drag 기록을 사이트의 에뮬레이터에서 다시 재생한다. (사용자 결정)
- 사이트 UI는 개인 디자인 시스템 `@eeennsu/web`으로 만들고, 디자인 작업은 design-flow로 한다. (사용자 결정)
- 레포와 사이트를 공개한다. GitHub 공개 레포에 올리고 GitHub Pages로 배포한다. (사용자 결정)

### 비목표

- 방문자가 코드를 직접 써서 돌리는 기능(브라우저 어셈블러, C 컴파일러). v1 뒤 반응을 보고 어셈블러부터 다시 정한다. (사용자 결정)
- 모바일 최적화. 데스크톱 우선으로 만든다. 모바일에서는 글을 읽을 수 있고 위젯이 동작하는 정도까지만 보장한다. (사용자 결정)
- 영어판. v1은 한국어만 쓴다. 영어판은 공개 직전에 다시 정한다. (사용자 결정)
- 공개 사이트에서 MCP로 조작하는 것. 기존 설계와 같다.
- 레포 학습 노트(`docs/learn`). 없앤다. (사용자 결정)
- 기존 비목표 중 진짜 안드로이드 부팅, ARM·x86 게스트, 성능 경쟁, RN 가상 폰, REA 동적 분석은 그대로다.

### 반목표 (동작하더라도 실패로 보는 것)

- 검수를 거치지 않은 챕터를 공개하는 것. 4.5절의 두 단계 검수(사실 대조, 사용자 읽기)를 모두 통과해야 공개한다.
- 사이트가 DS를 덮는 것. 범용 UI를 사이트 안에서 따로 만들거나, 토큰을 하드코딩하거나, DS 스케일 밖 임의값으로 메우는 것이 해당한다. design-flow 설계의 "하면 안 되는 것"을 따른다.
- 기존 반목표 중 남의 에뮬레이터 코드나 이미지를 붙여 동작만 시키는 것, 라이선스 위반, 마지막에 한꺼번에 동작하는 구조는 그대로 실패로 본다.
- 기존 반목표 "에이전트가 학습 노트를 대신 쓰는 것"은 지운다. 이제 설명 글은 에이전트가 쓴다. (사용자 결정)

## 3. 제약

- 기존 설계 3장을 모두 따른다. 윈도우 개발, 맥에서도 도는 node 스크립트, conventions 스킬, REA 대상 한정, 라이선스 규칙, 한국어 '-다'체 문서가 해당한다.
- **DS 버전.** 사이트는 npm에 배포된 `@eeennsu/web`을 정확한 버전으로 고정해 쓴다. `workspace:`나 로컬 경로로 연결하지 않는다. design-flow 훅이 `workspace:` 의존성을 소비 앱으로 보지 않기 때문이다.
- **DS의 전제 조건.** `@eeennsu/web`은 React 19 이상과 Tailwind CSS 4.1 이상을 peer로 요구한다(`design-system/packages/web/package.json`, 2026-10-19 확인).
- **호스팅.** GitHub Pages는 응답 헤더를 정할 수 없다. 기존 설계대로 SharedArrayBuffer(COOP/COEP)에 기대지 않는다. 라우팅은 Pages에서 새로고침해도 깨지지 않는 방식이어야 한다.
- **플러그인 호환.** 플러그인은 `apps/web` 빌드 결과를 복사해 로컬 서버로 서빙한다(`packages/mcp/scripts/buildPlugin.mjs`). React로 바꾼 뒤에도 MCP 모드(`?token=`) 페이지와 브리지, 스냅샷 저장이 지금처럼 동작해야 한다.

## 4. 구조

### 4.1 사이트 (`apps/web`)

- `apps/web`을 React + Vite 앱으로 바꾼다. (사용자 결정) 새 앱을 따로 만들지 않는다. worker·브리지·스냅샷 코드를 한 곳에서 쓰기 위해서다.
- 페이지는 셋으로 나뉜다. (설계자 판단)
  - 목차(첫 화면)
  - 챕터 페이지 8개
  - 에뮬레이터 페이지. 지금의 단독 에뮬레이터 화면이다. 플러그인은 이 페이지를 연다. 공개 사이트에서는 "놀이터"로 둔다.
- 챕터 콘텐츠는 MDX로 쓴다. 위젯은 MDX 안에 React 컴포넌트로 넣는다. (설계자 판단)
- 한 챕터 페이지는 에뮬레이터 인스턴스를 몇 개 쓸지, 위젯끼리 하나를 나눠 쓸지는 빌더가 정한다.

### 4.2 에뮬레이터 관찰·제어 기능

챕터 위젯이 쓰는 기능이다. 지금 core의 `Machine`은 `cpu`, `bus`, `ram`, 장치들을 이미 내보낸다. 그래서 대부분은 worker 메시지로 꺼내는 일이고, 새로 짜는 큰 부품은 역어셈블러와 버스 접근 기록 둘이다.

| 기능 | 쓰는 챕터 | 비고 |
|---|---|---|
| 멈춤, 계속, n개 명령 실행(단계 실행) | 1, 2, 3 | 지금은 연속 실행과 reset만 있다 |
| CPU 상태 읽기: pc, 레지스터 32개, 특권 모드, 주요 CSR(mstatus, mtvec, mepc, mcause, mie, mip), wfi 대기 여부 | 2 | |
| 레지스터·메모리 값 쓰기 | 2, 3 | "직접 해 보기"에서 값을 바꿔 본다 |
| 메모리 읽기(주소, 길이) | 1, 3, 4 | 프레임버퍼 구간 포함 |
| 역어셈블: 명령어 워드를 `addi a0, a0, 1` 같은 글자로 | 1, 2 | RV32IM + Zicsr + 이 에뮬레이터가 쓰는 특권 명령. core에 둔다 |
| ELF 정보: 진입 주소, 세그먼트 목록 | 1 | `loadElf`가 이미 돌려준다 |
| 메모리 맵 목록: 장치 이름, 주소 범위 | 3 | `memoryMap.ts`가 원본이다 |
| 버스 접근 기록: 장치 접근(주소, 폭, 읽기·쓰기, 값)을 켜고 끌 수 있는 기록 | 3, 4, 5 | 끈 상태에서는 실행 속도에 영향이 없어야 한다 |
| 터치 장치 상태: 래치 레지스터 값, 큐 깊이 | 5 | |
| 스냅샷 내용 보기: 메타, 구간별 크기 | 6 | |
| 입력 기록 재생: tap·drag 열을 시간 순서대로 넣기 | 7 | `tapEvents`, `dragEvents`가 이미 있다 |

- 이 기능들은 공개 사이트에서 쓰므로 브리지(MCP)를 거치지 않는다. 페이지와 worker 사이의 메시지로만 오간다. MCP 도구를 늘리지 않는다. (설계자 판단)
- 7장 재생에 쓸 기록은 실제 Claude 세션에서 플러그인으로 그린 tap·drag를 남겨 만든다. 기록 방법은 빌더가 정한다.

### 4.3 디자인

- 디자인 작업(챕터 화면, 위젯 모양, 에뮬레이터 페이지 다듬기)은 design-flow로 한다. design-flow는 다른 세션에서 만들고 있다. (사용자 결정)
- 범용 UI는 DS에 넣고, 에뮬레이터 전용 시각화는 사이트 안에 만든다. (사용자 결정)
  - DS에 넣는 것: Tabs, 표(Table), 코드 블록(CodeBlock), 긴 글 본문 스타일(Prose), 접기·펼치기(Collapsible). 4.4절의 DS 0.5.0이다. Collapsible은 모든 챕터의 확인 질문 답 펼치기와 접힌 비교 상자에 쓴다. (사용자 결정)
  - 사이트 안에 만드는 것: 레지스터 표, 메모리 hex 뷰, 단계 실행 컨트롤, 메모리 맵 그림, 버스 접근 기록 뷰 같은 에뮬레이터 전용 위젯. DS 컴포넌트와 DS 토큰(색, 간격, 글꼴)만으로 조립하고 임의값을 쓰지 않는다.
- 화면 구조 방향과 브랜드 색(DS가 허용하는 brand 변수 재선언)은 design-flow의 화면 구조 단계에서 사용자가 고른다.

### 4.4 DS 0.5.0 (design-system 레포)

이 작업에서 design-system 레포에 한 릴리스를 만든다. (사용자 결정)

- `@eeennsu/web`에 Tabs, Table, CodeBlock, Prose, Collapsible을 추가한다.
- 패키지 README의 "소비 규칙"은 이 작업이 아니라 design-flow 세션이 쓰고 0.4.1로 배포한다(design-flow 계획서 Task 2·3). 이 작업의 0.5.0은 0.4.1 위에 컴포넌트만 더한다. 배포가 두 번이 되는 것은 감수한다. (사용자 결정)
- 0.5.0 작업은 design-flow 세션의 README가 커밋되고 0.4.1이 배포된 뒤에 시작한다. 그전에는 같은 작업 트리에 그 세션의 미커밋 파일이 있으므로 design-system 레포에서 파일을 만들거나 커밋하지 않는다.
- 절차는 design-system 레포의 관례를 따른다. 아래는 2026-10-19에 그 레포를 읽고 확인한 것이다(경로는 design-system 레포 기준).
  - 계약이 늘어나는 변경은 스펙 개정 라운드로 한다. 스펙 상단 이력과 "R{n} 개정 요약"(`docs/design-system-spec.md`), 대안 비교 `docs/decisions-r{n}.md`, `docs/plan.md` 태스크, 구현 노트(`docs/implementation-notes.md`의 N·F 번호)를 남긴다. 직전 라운드가 R26이므로 이번은 R27이 된다(설계자 판단, Chip·Icon을 더한 R25 선례).
  - 웹 전용 컴포넌트는 허용된다. ButtonGroup·Tooltip·Dialog·Drawer·Form이 이미 웹 전용이다. 이번 네 개도 웹에만 넣고 native에는 넣지 않는다.
  - 새 컴포넌트는 `packages/tokens/src/contracts.ts`의 계약과 `webComponents`, `packages/web/src/index.ts`의 export와 `components` 맵에 모두 들어가야 한다. 빠지면 맵 동등성 테스트가 깨진다.
  - 계약 제약이 새 컴포넌트에도 걸린다. number 타입 prop 금지(C-14), 인터랙티브 컴포넌트는 `label` 필수(C-13), `as`·`render`·`asChild`·`style` 금지, 스타일은 `cn()`에 정적 클래스 문자열로 쓰고 semantic 토큰만 쓴다.
  - Tabs와 Collapsible은 이미 의존성에 있는 `@base-ui/react`(1.8.0)로 만든다. 새 의존성이 필요 없다. 설치된 1.8.0에 tabs가 있는 것은 확인했고, collapsible은 계획 단계에서 확인한다.
  - DS에는 고정폭 글꼴 토큰이 없다. Tailwind 기본 `--font-mono`가 리셋되지 않고 남아 있고, `docs/plan.md`의 S-7에 어휘 봉쇄의 예외로 적혀 있다. CodeBlock은 이 `font-mono`를 쓰고, R27에서 이 예외를 스펙의 알려진 동작으로 옮긴다. (설계자 판단)
  - CodeBlock은 0.5.0에서 문법 강조를 하지 않는다. 강조에는 새 의존성과 색 토큰이 필요하고 레포에 선례가 없다. 필요해지면 S2에서 design-flow의 DS 경계 결정으로 다시 묻는다. (설계자 판단)
  - Prose는 DS 토큰(글자 스텝, 간격, 색)으로 만든다. DS가 색·글자 크기·무게를 리셋하므로 Tailwind 타이포그래피 플러그인류는 그대로 쓸 수 없다.
  - 새 컴포넌트는 verify-next 화면에 올리고 Playwright 단언을 더한다. 웹 Chip·Icon을 "다음 웹 작업 때 올린다"고 미뤄 둔 항목도 이때 같이 처리한다.
  - 세 패키지는 lockstep으로 같은 버전(0.5.0)을 낸다. 에이전트는 버전 올리기, 빌드, 테스트, `verify:pack`까지 한다. npm 로그인과 `pnpm -r publish`는 패스키 2FA(패키지마다 한 번) 때문에 사용자가 자기 터미널에서 main 브랜치에서 한다.

### 4.5 콘텐츠 제작과 검수

챕터 하나는 다음 순서로 공개된다. (사용자 결정)

1. 에이전트가 설명 글, 위젯 배치, 직접 해 보기, 확인 질문, 비교 상자를 쓴다. 재료는 이 레포 코드와 `docs/guides`, `docs/rea`, `docs/research`다.
2. 별도 리뷰어(opus)가 글의 사실을 코드와 출처에 대조한다. 외부 사실(AOSP 소스 위치, 사양 문장)에는 출처와 확인일을 단다.
3. 사용자가 학습자로서 읽고 이해 안 되는 곳을 표시한다. 에이전트가 고친다.
4. 공개한다.

- `docs/guides`와 `docs/rea`는 챕터 재료로 남긴다. 공개 레포에 들어가므로 로컬 사용자 경로(`C:\Users\...`)는 공개 전에 지운다(후속 작업 목록에 있는 항목).
- 확인 질문의 답은 사이트에 함께 싣는다. 독자가 펼쳐 본다.

### 4.6 공개

- v1을 공개할 때 GitHub 공개 레포를 만들고 GitHub Pages로 배포한다. (사용자 결정)
- v1에는 리눅스 이미지가 없으므로 GPL 이미지 배포 의무(legal-info)가 생기지 않는다. riscv-tests 바이너리 같은 테스트 픽스처의 라이선스 표시는 공개 전에 확인한다.
- [후속 작업 목록](../followups/2026-10-19-amulator-m0-m1.md)의 "M5 공개 전에 처리할 것"은 v1 공개 전에 처리한다.

- 기존 설계 5장의 측정 관문(M2 60초, M3a 재측정, M3b 반응 200 ms)은 S4 이후에 그대로 적용한다.

## 6. 다른 작업에 넘기는 것

design-flow 세션(my-agent-setup)에 전할 요구사항이다. 이 작업은 design-flow를 만들지 않는다.

- **모노레포 대응.** design-flow 훅이 세션 폴더에서 처음 만나는 `package.json`에 `pnpm-workspace.yaml`이나 `workspaces`가 있으면, 멤버 패키지의 의존성까지 보고 DS 소비 앱인지 판정하게 넓힌다. amulator는 DS 의존성이 `apps/web`에만 있어서 루트에서 연 세션에서는 지금 훅이 켜지지 않는다. design-flow 설계 "범위 밖"의 "모노레포 루트에서 연 세션" 항목을 이 경우로 연다. (사용자 결정)
- **DS 버전 순서.** design-flow 세션이 README와 0.4.1을 먼저 낸다. 이 작업의 0.5.0은 그 뒤에 컴포넌트만 더한다. design-flow 세션은 0.5.0을 기다리지 않는다.
- **웹 열 실측.** design-flow 설계는 웹 열 실측을 첫 웹 소비 앱으로 미뤘다. amulator 사이트(S2)가 그 앱이다.

## 7. 성공 기준

### S1

- React로 바꾼 `apps/web`에서 지금 있는 테스트(`pnpm test`)와 플러그인 스모크(`pnpm smoke:plugin`), MCP 끝에서 끝까지 확인 스크립트가 모두 통과한다. 플러그인으로 그림판에 그리는 M1 데모가 지금처럼 된다.
- 4.2절 기능 각각에 테스트가 있다. 역어셈블러는 guest 프로그램과 riscv-tests ELF의 코드 구간을 LLVM `llvm-objdump` 출력과 대조해 같은 결과를 낸다.
- 버스 접근 기록을 끈 상태에서 실행 속도(MIPS)가 S1 전과 같은 수준이다. 비교 방법은 빌더가 정한다.
- DS 0.5.0이 npm에 배포되어 있고, 컴포넌트 5종(Tabs, Table, CodeBlock, Prose, Collapsible)이 계약·테스트·verify-next 화면과 함께 들어 있다.

### v1

- 챕터 0~7이 4.5절 검수를 모두 거쳐 공개되어 있다.
- GitHub Pages의 공개 URL에서 모든 챕터의 위젯이 동작한다. 새로고침해도 페이지가 깨지지 않는다.
- 사이트 코드에 design-flow 마무리 검사 대상(className 임의값, 하드코딩 hex, fontFamily 리터럴, DS 스케일 밖 간격)이 0건이다.

## 8. 빌더에게 맡기는 것

- 라우터 종류와 Pages 라우팅 방식(새로고침에 깨지지 않을 것)
- MDX 처리 도구와 설정
- worker 메시지 세부, 단계 실행·버스 접근 기록의 구현 방식
- 역어셈블러 구조와 출력 표기(LLVM 표기와 맞출 범위)
- 챕터 페이지의 에뮬레이터 인스턴스 수
- 7장 재생 기록을 남기는 방법과 파일 형식
- React 전환 중 지금 화면 모습을 옮기는 방식(기존 CSS 유지 등). 단, 새 디자인 결정은 하지 않는다

## 9. 위험과 대응

| 위험 | 대응 |
|---|---|
| design-flow가 늦어져 S2를 시작하지 못한다 | S1에서는 디자인 작업을 하지 않는다. S2는 design-flow가 준비될 때까지 기다린다. 오래 걸리면 그때 사용자와 다시 정한다 |
| React 전환이 플러그인 페이지(브리지, `?token=`, OffscreenCanvas 넘기기)를 깨뜨린다 | 7장 S1 기준의 스모크와 끝에서 끝까지 확인을 전환 직후 돌린다. OffscreenCanvas는 한 번만 넘길 수 있으므로 React의 개발 모드 이중 마운트에 주의한다 |
| 챕터 설명에 사실 오류가 들어간다 | 4.5절의 사실 대조와 사용자 읽기를 거친다 |
| DS 0.5.0 범위가 커진다 | 컴포넌트는 5종으로 고정한다. 그 밖에 필요한 것이 생기면 S2에서 design-flow의 DS 경계 멈춤으로 사용자에게 묻는다 |
| design-flow 세션과 design-system 작업 트리가 겹친다 | 4.4절대로 0.4.1 배포 뒤에 시작한다. 시작할 때와 커밋 직전에 브랜치와 status를 확인하고, 내가 만들지 않은 변경은 커밋에서 뺀다 |
| 플러그인 스모크가 서버 HTML에서 `<canvas`를 찾는데, React로 바꾸면 canvas가 클라이언트에서 그려진다 | S1에서 스모크 검사를 React 페이지에 맞게 고친다 |
| 버스 접근 기록이 실행 루프를 느리게 한다 | 기록을 끈 상태의 비용이 없도록 짜고, 7장 S1 기준으로 확인한다 |

## 10. 남은 미확인 사항

- GitHub Pages의 파일·사이트 크기 한도. v1의 ELF는 수 KB라 문제가 되지 않을 것으로 보지만 공개 전에 조회한다.
- riscv-tests 픽스처를 공개 레포에 포함할 때의 라이선스 표시 방식.
- design-flow가 준비되는 시점.
