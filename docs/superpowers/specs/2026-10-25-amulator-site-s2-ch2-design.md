# amulator 학습 사이트 S2-1 설계: 챕터 틀과 2장 CPU

- 날짜: 2026-10-25
- 상위 설계: [2026-10-19-amulator-learning-site-design.md](2026-10-19-amulator-learning-site-design.md) 5장 S2. 그 설계의 1~4장, 7~9장을 따른다. 이 문서는 S2의 첫 묶음만 정한다.
- 이어 받는 것: S1(가) 후속 목록 [2026-10-22-amulator-site-s1.md](../followups/2026-10-22-amulator-site-s1.md)의 "S2 첫 위젯 전에 정할 것"

## 1. 의도

S2는 챕터 0~7을 만드는 단계다. 첫 묶음에서는 모든 챕터가 함께 쓸 **챕터 화면 틀**을 정하고, 그 틀로 **2장 CPU 하나를 검수까지** 끝낸다. 나머지 챕터는 같은 틀에 내용만 바꿔 넣는다. (사용자 결정: 2장부터)

2장을 고른 이유(설계자 판단, 사용자 동의): 단계 실행, 레지스터 강조, 역어셈블 한 줄이 모두 들어가고, S1에서 만든 기능(단계 실행·상태 읽기·역어셈블러)을 바로 쓴다.

## 2. 목표, 비목표, 반목표

### 목표

- 챕터 화면 틀(3장)을 `apps/web`에 만든다. DS `@eeennsu/web` 0.5.0을 정확한 버전으로 설치하고 그 컴포넌트와 토큰으로 조립한다.
- 2장 CPU의 단계 흐름(4장)과 내용을 만들고, 상위 설계 4.5절 검수 중 1~3번(작성 → 사실 대조 → 사용자 읽기)을 끝낸다. 공개(4번)는 S3다.
- 목차 페이지: 챕터 8개 목록과 각 챕터로 가는 링크. 아직 없는 챕터는 "준비 중"으로 보인다.
- 에뮬레이터 페이지(놀이터)와 플러그인 MCP 모드는 지금처럼 동작한다.

### 비목표

- 2장 밖의 챕터 내용. 틀은 다른 챕터가 쓸 수 있게 만들지만 내용은 넣지 않는다.
- GitHub Pages 배포와 공개(S3).
- 장치 접근 기록의 필터·합치기(후속 목록 Important). 2장은 장치 기록 탭을 주인공으로 쓰지 않는다. 3장을 만들 때 정한다.
- 스냅샷 구간 보기 UI, 기록 재생 UI(6·7장).

### 반목표

- design-flow를 거치지 않은 디자인. 색·간격·위계는 design-flow로 정하고, 마무리 검사(className 임의값, 하드코딩 hex, fontFamily 리터럴, DS 스케일 밖 간격) 0건이어야 한다.
- 사이트 안에 범용 UI를 따로 만드는 것. 탭·표·코드 블록·접기는 DS 0.5.0 컴포넌트를 쓴다.
- 검수를 거치지 않은 2장을 "완성"으로 표시하는 것.
- 챕터 위젯이 놀이터에 저장한 상태를 덮거나 지우는 것.

## 3. 챕터 화면 구조 (사용자 결정, 2026-10-25 비주얼 컴패니언 시안 B)

데스크톱 기준이다.

- **왼쪽(넓게): 에뮬레이터 열**
  - 에뮬레이터 화면(canvas)
  - 그 아래 작은 UART 터미널. 모든 챕터에서 늘 보인다. hello·clock처럼 글자로만 출력하는 프로그램도 결과가 보이게 하려는 것이다. (사용자 결정, 빌더 점검 질문 1)
  - 실행 줄: [멈춤] [한 단계] [계속], 현재 pc와 그 명령어의 역어셈블 한 줄
  - 들여다보기 탭: 레지스터 · 메모리 · 장치 기록. DS Tabs를 쓴다. 단계가 바뀌면 그 단계가 지정한 탭이 열리고, 방금 바뀐 값이 강조된다.
- **오른쪽(좁게): 단계 흐름**
  - 챕터를 단계 카드 몇 개로 나눈다. 지금 단계만 펼쳐지고 지난 단계는 ✓로 접힌다.
  - 카드 하나: 짧은 설명(3~4줄, 긴 설명은 카드 안에서 접는다), [해 보기] 버튼, 확인 질문(DS Collapsible로 답 펼치기).
  - [해 보기]가 왼쪽 에뮬레이터를 움직인다. 이것이 이 화면의 핵심이다.
  - 맨 아래: "진짜 안드로이드 에뮬레이터는" 상자(기본 접힘, Collapsible + Card).
- 모바일: 에뮬레이터 열 → 단계 흐름 순으로 위아래로 쌓는다. 읽을 수 있고 위젯이 동작하는 정도만 보장한다(상위 설계 비목표).

설계자 판단(사용자에게 알림, 반대 없음):
- 챕터 페이지마다 에뮬레이터 인스턴스는 하나다. 들여다보기 탭은 에뮬레이터 화면 **바깥 아래**에 둔다. DS Tabs는 숨은 패널을 마운트하지 않으므로 화면을 탭 안에 두면 탭을 바꿀 때 에뮬레이터가 다시 켜진다(후속 목록).
- 챕터 에뮬레이터는 상태를 저장하지 않는다. 열 때마다 단계가 정한 시작 상태에서 시작한다. 저장·복원은 놀이터에서만 한다. 후속 목록의 "공유 스냅샷 저장소" 문제를 이렇게 피한다.

## 4. 2장 CPU 단계 흐름 (설계자 판단, 사용자 승인 2026-10-25)

게스트는 `guest/baremetal`의 **clock 하나**다. 처음 표는 1~4단계에 hello를 썼지만, hello는 전역 변수가 없어 `.bss`가 비어(`_bss_start` = `_bss_end` = `0x80000174`, 빌더 점검이 ELF 심볼로 확인) 3단계의 반복이 한 번도 돌지 않는다. clock은 시작 코드(`start.S`)가 같고 `.bss`가 16바이트라 반복이 4번 돈다. (사용자 결정, 빌더 점검 질문 3)

각 단계는 "시작 상태(어느 주소까지 실행해 둔 상태인지)와 여는 탭"을 정한다.

| # | 단계 | 시작 상태 | 여는 탭 | 해 보기 |
|---|---|---|---|---|
| 1 | 명령어 하나 꺼내기 | 멈춘 채 진입 주소(0x80000000) | 메모리(pc 주변) | [한 단계] → pc가 4 는다. 그 주소의 4바이트가 명령어(역어셈블 한 줄)라는 것을 본다 |
| 2 | 해석하고 실행하기 | `la sp` 앞 | 레지스터 | `la sp`, `csrw mtvec`을 한 단계씩 → sp, t0이 바뀌어 강조된다 |
| 3 | 반복과 분기 | `.bss` 반복 첫 `bgeu` 앞 | 레지스터 | 반복(`bgeu`, `sw`, `addi`, `j`) → pc가 되돌아가고 a0이 4씩 커진다 |
| 4 | 값을 바꿔 보기 | 내용 작성 때 정한 주소 앞 | 레지스터 | 레지스터 하나를 고치고 실행해 결과(레지스터 또는 터미널 글자)가 달라지는 것을 본다. 무엇을 고칠지는 내용 작성 때 실제 역어셈블로 정한다 |
| 5 | 트랩 | 실행 중 | 레지스터(CSR 포함) | 타이머 인터럽트가 와서 pc가 mtvec(`trap_entry`)에 오면 멈춘다 → mcause와 mepc에 이유와 돌아올 주소 → `mret` 주소에서 다시 멈춘 뒤 한 단계로 원래 자리에 돌아간다. 터미널에 `uptime` 출력이 이어진다 |
| 6 | 진짜 안드로이드 에뮬레이터는(접힘) | — | — | QEMU의 TCG(명령어를 묶어 번역)와 이 에뮬레이터의 한 개씩 해석을 비교한다. AOSP·QEMU 소스 링크와 확인일 |

- 사양 세부(예: mret 뒤 MPIE 값)는 다루지 않는다(상위 설계 1장 목표 수준).
- 단계 3·4의 정확한 명령어 범위와 고칠 레지스터는 내용 작성 때 실제 역어셈블로 정한다.

**단계 사이의 상태 (사용자 결정, 빌더 점검 질문 2)**
- 단계마다 정해진 시작 상태가 있다. 단계에 들어가거나 카드의 [이 단계 처음으로]를 누르면 "멈춘 채 다시 시작 → 그 단계의 주소까지 실행 → 멈춤"으로 그 상태를 만든다.
- 학습자는 [계속]이나 [한 단계]로 자유롭게 움직여도 된다. 상태가 어긋나면 [이 단계 처음으로]로 돌아온다.
- 지난 단계 카드도 다시 펼칠 수 있고, 펼치면 그 단계의 시작 상태로 맞춘다.
- 진행도는 저장하지 않는다. 새로고침하면 1단계부터다.

## 5. 새로 필요한 기능

S1 worker 메시지(멈춤·계속·단계 실행·상태 읽기·레지스터 쓰기·메모리 엿보기)에 더한다. 관찰·제어는 페이지와 worker 사이 메시지로만 오간다(상위 설계 4.2).

1. **주소에서 멈추기.** 실행 중 pc가 지정한 주소에 오면 멈추고 상태를 알린다. 단계 시작 상태를 만들 때(2~4단계)와 5단계의 mtvec·`mret`에서 쓴다. 주소 하나이고, 한 번 걸리면 꺼진다(설계자 판단: 게스트 시계는 멈춘 동안에도 흘러 다시 걸리는 혼선을 막는다). 여러 개, 조건부는 만들지 않는다.
2. **멈춘 채 다시 시작하기.** S1의 "부팅 전 pause"와 "멈춘 채 reset"을 쓴다. 2장은 clock 하나라 챕터 안에서 프로그램을 바꾸지 않는다. 틀은 다른 챕터를 위해 단계가 프로그램을 정할 수 있게 둔다.
3. **저장하지 않는 인스턴스.** 챕터 에뮬레이터는 스냅샷 저장소를 쓰지 않는다(읽지도 지우지도 않는다). 놀이터와 MCP 모드는 지금처럼 저장한다.
4. **바뀐 값 강조.** 직전 상태와 지금 상태(`MachineView`)를 페이지에서 비교한다. worker를 바꾸지 않는다.
5. **wfi 중 단계 실행.** clock은 wfi로 쉰다. 쉬는 중에 [한 단계]가 0개를 실행하고 조용히 끝나는 문제(후속 목록)를, 상태에 "쉬는 중"(`CpuView.idle`)을 보이는 것으로 드러낸다. 실행된 명령 수를 상태에 실을지는 빌더가 정한다.

후속 목록에서 이번에 함께 처리하는 것: reset 뒤에는 `booted`를 기다린 다음 inspect한다는 계약을 `messages.ts`에 적는다. 메모리 탭에 주소 입력을 두면 `peekMemory`의 부호 있는 주소 문제(`>>> 0`)를 같이 고친다.

## 6. 디자인 진행 (design-flow)

- 디자인은 design-flow로 한다(상위 설계 4.3). superpowers가 무엇을 만들지를, design-flow가 어떻게 보일지를 맡는다.
- **화면 구조는 3장으로 정했다.** design-flow "새 화면·새 흐름" 2번의 화면 구조 단계를 brainstorming 대화의 비주얼 컴패니언으로 대신했다. 웹 UI 플러그인(impeccable)이 이 프로젝트에서 아직 꺼져 있어 `impeccable shape`는 돌리지 않았다. (설계자 판단)
- 준비할 것(전역 지시):
  - `apps/web`에 `@eeennsu/web` 0.5.0과 Tailwind CSS 4.1 이상(DS peer)을 설치한다.
  - 프로젝트 `.claude/settings.json` `enabledPlugins`에 웹 UI 플러그인(impeccable, ui-ux-pro-max)을 켜고, CLAUDE.md에 `@~/my-agent-setup/docs/web.md` 스킬 선택표를 넣는다.
- **design-flow 모노레포 대응이 아직 없다**(2026-10-24 확인). 훅과 라우터는 작업 폴더에서 처음 만나는 `package.json`만 본다. 디자인 단계를 돌릴 때는 `apps/web`을 작업 폴더로 삼아 라우터 1단계가 `apps/web/package.json`을 읽게 한다. (설계자 판단)
- 색: 브랜드 색(DS가 허용하는 brand 변수 재선언)은 design-flow 진행 중에 사용자가 고른다(상위 설계 4.3). 그 자리에서 멈추고 묻는다.
- 계획서 마지막 태스크는 design-flow의 "디자인 마무리"(다듬기 → 모션 → 비평·감사 → 실제 화면 확인 → 마무리 검사 → 기록)이고, 메인 세션이 돌린다.

## 7. 내용과 검수

- 설명 글, 단계, 확인 질문(답 포함), 비교 상자는 에이전트가 쓴다. 재료는 이 레포 코드, `docs/guides`, `docs/rea`, `docs/research`다.
- 사실 대조: 별도 리뷰어(opus)가 글의 사실을 코드와 출처에 대조한다. 외부 사실(QEMU·AOSP 소스 위치, 사양 문장)에는 출처 URL과 확인일을 단다.
- 사용자 읽기: 사용자가 학습자로서 읽고 이해 안 되는 곳을 표시하면 에이전트가 고친다. 이 단계에서 진행이 사용자를 기다린다.
- 사람이 읽는 한국어 글이므로 다 쓰면 `korean-humanizer`로 한 번 다듬는다(전역 지시).

## 8. 성공 기준

- 목차 → 2장 → 6단계를 차례로 따라가며 [해 보기]가 모두 동작한다. 5단계에서 트랩 진입 시 멈추고 mcause·mepc가 보인다.
- 아무 단계에서 [계속]으로 상태를 흐트러뜨린 뒤 [이 단계 처음으로]를 누르면 그 단계의 시작 상태로 돌아온다. 지난 단계를 다시 펼쳐도 같다.
- 챕터 화면이 3장 구조이고, design-flow 마무리 검사 0건이다.
- 챕터 에뮬레이터를 쓴 뒤에도 놀이터 저장본이 그대로다.
- `pnpm typecheck` · `lint` · `format:check` · `test`, 플러그인 스모크, MCP 끝에서 끝까지 확인이 통과한다.
- 2장이 사실 대조와 사용자 읽기를 거쳤다.

## 9. 빌더에게 맡기는 것

- 라우터 종류와 Pages에서 새로고침해도 깨지지 않는 방식(상위 설계 8장). S1은 HTML 진입점 두 개로 나눴다.
- MDX 처리 도구와, 단계 카드를 MDX로 쓰는 방식(단계마다 시작 상태·탭·해 보기를 어떻게 적을지).
- 주소에서 멈추기의 메시지 모양과 실행 루프 안 검사 위치. 꺼져 있을 때 실행 속도 영향이 없어야 한다(S1 벤치 기준).
- 터미널의 크기와 모양(DS 토큰 안에서, design-flow 다듬기). `mountEmulator`는 지금처럼 터미널 자리를 받는다.
- 바뀐 값 강조의 모양(design-flow 다듬기에서 정한다).
- 레지스터 표·메모리 hex 뷰 같은 에뮬레이터 전용 위젯의 내부 구조. DS 컴포넌트와 토큰만으로 조립한다.

## 10. 미확인

- design-flow 진행 중에 고를 브랜드 색.
- impeccable 등 웹 UI 플러그인이 이 레포에서 켜지는지(윈도우 심볼릭 링크 문제가 있으면 `fix-plugin-symlinks.mjs`).
