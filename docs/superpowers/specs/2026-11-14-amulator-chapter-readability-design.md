# amulator 챕터 화면 가독성 설계: 첫 화면 예산과 동작 박자 카드

- 날짜: 2026-11-14
- 바꾸는 설계: [2026-10-25-amulator-site-s2-ch2-design.md](2026-10-25-amulator-site-s2-ch2-design.md) 3장(챕터 화면 구조)의 왼쪽 열 순서와 카드 구성. 그 문서의 나머지(4~9장)는 그대로 따른다.
- 이어 받는 것: [후속 목록](../followups/2026-10-25-amulator-site-s2-ch2.md) "화면"의 버튼과 바뀐 값의 거리, 빈 canvas, 4단계 결과 줄 길이와 "글·데이터"의 3단계 본문 길이
- 출발점: 2026-11-14 아이디어 문서의 1번(동작 박자 카드)과 2번(첫 화면 예산). 3번(더 읽기 해체), 4번(글 속 이름 누르기), 5번(답 잠금)은 이번 범위가 아니다.

## 1. 의도

2장을 읽은 사용자가 오른쪽 설명 패널이 안 읽히고 한눈에 안 들어온다고 했다. 2026-11-08에 위계·색·목록을 고친 뒤에도 같았다. 원인은 둘이다.

- 글이 UI의 일을 떠맡았다. "레지스터 탭에서 `a2`가 강조된다" 같은 길 안내, 버튼 설명, 박아 둔 주소가 본문에 섞여 글이 길다.
- 글이 가리키는 표가 화면 밖에 있다. 버튼을 누르는 곳과 값이 바뀌는 곳이 730px 떨어져 있다.

이번 작업은 글의 그 일을 데이터와 컴포넌트로 옮기고, 누르고 보는 고리가 첫 화면 안에서 닫히게 한다. 남은 7개 장이 이 틀을 물려받으므로 2장을 다 만든 지금 바꾼다.

## 2. 목표, 비목표, 반목표

### 목표 (사용자 결정, 2026-11-14)

- **첫 화면 기준.** 1900x940에서 다음 넷이 스크롤 없이 보인다: "왜" 글, 지금 누를 버튼, 바뀐 값 앞→뒤, 표에서 그 값이 있는 줄. 확인 질문과 표의 나머지는 스크롤해도 된다.
- **왼쪽 열: 위 띠.** 화면을 안 쓰는 장은 canvas를 줄여 터미널 옆에 두고, 그 아래에 실행 줄과 들여다보기 탭을 둔다. 레지스터 표는 한 줄에 4쌍으로 넓힌다(3장).
- **카드: 목록, 지금 것만 펼침.** 동작 이름은 모두 보이고, 설명 한 줄과 값 표는 방금 한 동작과 다음 동작에만 붙는다(4장).
- **데이터.** 동작 설명 한 줄과 "볼 곳"은 `steps.ts`의 동작 객체에 적는다(5장).
- 2장의 다섯 단계 글을 이 틀에 맞게 고쳐 쓰고 검수(사실 대조 → 사용자 읽기)를 다시 거친다(6장).

### 비목표

- 더 읽기의 재구성, 글 속 레지스터 이름을 누르는 컴포넌트, 확인 질문 답 잠금(아이디어 3~5번).
- canvas를 쓰는 장의 새 배치. `screen: 'full'`인 장은 지금 배치를 그대로 쓴다. 표를 canvas 옆에 두는 배치는 4장을 만들 때 정한다.
- "볼 곳"에 적은 줄을 누르기 전부터 표에서 표시하는 기능.
- 글 예산을 강제하는 테스트. 예산은 쓰는 규칙으로만 둔다(6장).
- 메모리 표를 8바이트 줄로 바꾸기, 터미널 크기 옵션. 위 띠 배치에서는 둘 다 지금 크기로 들어간다.
- 후속 목록의 다른 항목(오류 문구 위치, 상태 줄 문구, 터치 타깃 등).
- 모바일 최적화. 읽을 수 있고 위젯이 동작하는 정도만 보장한다(상위 설계).

### 반목표

- 에뮬레이터가 다시 켜지는 변경. canvas와 터미널 자리는 다시 마운트하지 않는다.
- 글을 줄이다가 확인 질문의 답이 기대는 사실을 잃는 것.
- 왼쪽 [한 단계]·[계속]이 학습자가 연 탭을 바꾸는 것.
- design-flow를 거치지 않은 디자인. 마무리 검사(className 임의값, 하드코딩 hex, fontFamily 리터럴, DS 스케일 밖 간격)는 0건이어야 한다.
- 놀이터(`emulator.html`)와 플러그인 MCP 모드의 동작 변화.

## 3. 왼쪽 열: 위 띠

### 실측 (2026-11-14, 1900x940, agent-browser)

| 대상 | 값 |
|---|---|
| 열 폭 | 왼쪽 720, 오른쪽 472 (`max-w-7xl`, `lg:grid-cols-5` 3:2). 뷰포트 1344px 이상에서는 같다 |
| canvas | 320x480, y140~620 |
| 터미널 | 482x182 (60열 12줄), y636~818 |
| 실행 줄 / 탭 머리 / 표 | y886 / y932 / y990 |
| 레지스터 표(2쌍) | 내용 폭 312, 높이 805(20줄, 줄 높이 37). `a0` 줄은 표 위에서 583 |
| 메모리 표 | 내용 폭 412, 높이 176 |
| 3단계 | [bgeu 실행] 버튼 y843, `a0` 줄 y1573 |
| 카드 높이(더 읽기 접음) | 1단계 732, 2단계 780, 3단계 896 |

지금 순서에서는 canvas를 없애도 `a0` 줄이 첫 화면에 들지 않는다. 표가 805px라 탭이 y320 위에서 시작해야 하기 때문이다. 그래서 표를 가로로 넓힌다.

### 배치

장이 화면 크기를 선언한다. `ChapterContent`에 `screen: 'small' | 'full'`을 더한다. 장 단위이고 단계마다 바꾸지 않는다(설계자 판단). 2장은 `'small'`이다. 다른 장의 값은 그 장을 만들 때 정한다.

`screen: 'small'`일 때 왼쪽 열은 이렇다.

```
┌canvas ┐ ┌────────── 터미널 60열 ──────────┐
│ 줄임   │ │                                  │
└───────┘ └──────────────────────────────────┘
상태 줄 · 알림
[멈춤] [한 단계] [계속]  pc 8000002c  addi a0, a0, 0x4
[레지스터] [메모리] [장치 기록]
 pc        mstatus    mtvec      mepc
 mcause    mie        mip
 x0 zero   x8  s0     x16 a6     x24 s8
 x1 ra     x9  s1     x17 a7     x25 s9
 x2 sp     x10 a0     x18 s2     x26 s10
 …         …          …          …
 x7 t2     x15 a5     x23 s7     x31 t6
```

- canvas는 CSS로만 줄인다. 시안의 크기는 터미널 높이에 맞춘 121x182(320x480의 약 1/3, 비율 유지)다. 정확한 크기는 DS 스케일 안에서 design-flow 다듬기가 정한다.
- 터미널, 메모리 표, 장치 기록은 지금 크기와 모양 그대로다.
- 레지스터 표는 한 줄에 4쌍이다. pc와 CSR 여섯이 두 줄, x 레지스터가 여덟 줄(x0~7, x8~15, x16~23, x24~31이 한 칸씩)이다. 머리 줄을 더해 약 407px라 1900x940에서 표 전체가 첫 화면에 든다(계산: 표 위 y442, 바닥 y849).
- 4쌍 표의 폭은 2쌍 실측의 두 배인 약 624px로 어림했다. 재지 않았다. 왼쪽 열이 그보다 좁은 화면에서는 지금의 2쌍으로 돌아간다. 왼쪽 열은 뷰포트 1344px 이상에서 720px이므로 `xl`(1280px) 근처가 경계다.
- `lg` 미만(한 열로 쌓이는 화면)에서는 띠가 줄바꿈되고 표는 2쌍이다.

`screen: 'full'`일 때는 지금 배치(canvas → 터미널 → 상태 → 실행 줄 → 탭, 2쌍 표)를 한 글자도 바꾸지 않는다.

이 배치는 2026-10-25 설계 3장의 왼쪽 열 순서(사용자가 고른 시안 B)를 `'small'`인 장에서 바꾼다. 사용자가 2026-11-14 와이어프레임을 보고 다시 골랐다.

## 4. 카드: 목록, 지금 것만 펼침

```
③ 반복과 분기
왜 (문단 하나, 세 문장 이하)
▸ 더 읽기
────────────────────────────────
해 보기                    3/5 해 봄
✓ bgeu 실행
✓ sw 실행
✓ addi 실행
   `a0`을 4 올린다.
   ┌ a0  80000310 → 80000314 ┐
   └ pc  8000002c → 80000030 ┘
4 [j 실행]
   맨 위로 돌아간다.
   볼 곳: 실행 줄의 pc
5 한 바퀴 더
────────────────────────────────
확인 질문
▸ 이 반복은 몇 바퀴 돌고 끝나나? …
다음: 값을 바꿔 보기 →   ↺ 처음 상태로
```

동작마다 상태가 넷이다. 해 본 동작 수를 `done`이라 하면:

| 동작 | 보이는 것 |
|---|---|
| 방금 한 동작(`done - 1`번째) | ✓, 이름, 설명 한 줄, 값 표 |
| 그보다 앞서 한 동작 | ✓, 이름 |
| 다음 동작(`done`번째) | 번호, 버튼(이름), 설명 한 줄, "볼 곳" |
| 그 뒤 동작 | 번호, 흐린 이름 |

- **값 표.** 줄은 그 동작의 `look.fields`에 적은 값, 그다음 `pc`(바뀌었을 때만)다. 줄마다 이름, 앞 값 → 뒤 값을 보인다. 그 밖에 바뀐 값은 표 아래 "외 n개" 한 줄로 줄인다. 4단계 [uptime 출력까지 실행]처럼 `a0`~`a6`이 바뀌는 동작이 이 규칙을 탄다.
- **앞 값이 없을 때.** 5단계 첫 동작처럼 누르기 전 상태가 실행 중이면 뒤 값만 보인다.
- **`setRegister`.** `pc`가 안 움직이므로 고친 레지스터 한 줄만 보인다.
- **실패.** 동작이 실패하면 값 표를 지운다(지금 "방금" 줄을 지우는 것과 같다). 오류 알림의 위치는 바꾸지 않는다.
- **다 했을 때.** 목록 아래에 지금의 "다 해 봤다…" 안내가 남고, 버튼은 없다.
- **처음 상태로.** `done`이 0이 되어 값 표가 사라진다.
- **탭.** [해 보기] 버튼을 누르면 그 동작의 `look.place`가 들여다보기 탭이면 그 탭을 연다. 왼쪽 [한 단계]·[계속]은 탭을 바꾸지 않는다. 단계에 들어갈 때 여는 탭(`step.tab`)은 그대로다.
- **없어지는 것.** "누르면 에뮬레이터가 명령어 하나를 실행한다" 안내 줄(`hintText`)과 "✓ 방금: … · 바뀐 값: a0" 결과 줄(`resultText`). 설명 한 줄과 값 표가 그 자리를 맡는다.
- **낭독.** 지금 결과 줄이 있는 `role='status'` 영역은 남긴다. 방금 한 동작의 결과가 그 안에서 읽힌다.
- 더 읽기, 확인 질문, 다음·처음 상태로 버튼, 지난·남은 단계 줄, 안드로이드 상자는 바꾸지 않는다.
- 레지스터 표의 바뀐 값 강조(`useChangedFields`)도 그대로다. 값 표와 표의 강조가 같은 값을 두 곳에서 보인다.

### 카드가 첫 화면을 넘을 때 (설계자 판단)

지난 단계 줄은 지금 카드 위에 쌓인다. 그래서 단계가 뒤로 갈수록 카드가 아래로 밀린다(3단계는 두 줄, 5단계는 네 줄. 3단계에서 약 80px로 어림했고 재지 않았다). 새 카드의 실제 높이도 모른다(11장). 그래서 순서를 이렇게 둔다.

1. 배치와 카드를 만든 직후, 글을 다듬기 전에 다섯 단계를 1900x940에서 잰다.
2. 9장 첫 기준을 넘는 단계가 있으면 그 단계의 본문을 두 문장으로 줄이고 뺀 사실을 더 읽기로 옮긴다.
3. 그래도 넘으면 멈추고 실측 값과 함께 사용자에게 묻는다.

지난 단계 줄을 접거나 옮기기, 페이지 머리 줄이기, 누를 때 자동으로 스크롤하기는 사용자 결정 없이 하지 않는다. 지난 단계 줄의 모양은 사용자가 2026-11-08에 시안 넷 중에서 고른 것이다(후속 목록 판정 11).

## 5. 데이터

동작 객체에 두 필드를 더한다(사용자 결정: 전부 `steps.ts`에).

```ts
{
  label: 'addi 실행',
  kind: 'step',
  count: 1,
  line: '`a0`을 4 올린다.',
  look: { place: 'registers', fields: ['x10'] },
}
```

- `line`: 그 동작이 하는 일 한 문장이다. 백틱으로 감싼 부분은 인라인 코드로 보인다. 다른 서식은 없다.
- `look.place`: `'registers' | 'memory' | 'devices' | 'runLine' | 'terminal'` 중 하나다. 앞 셋은 들여다보기 탭이고, 뒤 둘은 실행 줄과 터미널이다.
- `look.fields`: 값 표에 보일 값의 키다. `changedFields`가 쓰는 키(`'pc'`, `'x0'`~`'x31'`, CSR 이름)와 같다. 없어도 된다(메모리, 터미널을 보는 동작).
- "볼 곳" 문구는 `look`에서 만든다. 탭 이름과 레지스터 이름이 화면과 같은 출처(`TAB_LABELS`, `ABI_REGISTER_NAMES`)에서 나와 글과 화면이 어긋나지 않는다.
- 두 필드는 모든 동작에 필수다. 타입이 빠뜨림을 잡는다.

MDX는 지금처럼 본문, `<More>`, `<Try />`, `<Checks>`로 이룬다. `<Try />`가 동작 목록을 그린다. MDX 컴포넌트 목록은 늘지 않는다.

기각한 방법은 8장에 있다.

## 6. 글

2장의 다섯 단계를 고쳐 쓴다.

- **본문.** `<Try />` 위 본문은 문단 하나, 세 문장 이하다. 이 단계가 왜 있는지와 무엇을 보게 되는지만 말한다(설계자 판단. 시안의 3단계 본문이 세 문장이다).
- **동작 줄로 옮기는 것.** 어디를 보라는 문장, 버튼이 무엇을 하는지 설명하는 문장, 3단계의 네 줄 목록, 더 읽기 안의 버튼 설명("[한 바퀴 더]는 한 바퀴를 한 번에 돈다").
- **더 읽기로 옮기는 것.** 본문에서 빠지지만 확인 질문의 답이나 뒤 단계가 기대는 사실. 예: 1단계의 "표와 `pc`는 주소를 `0x` 없이 찍는다".
- **`line`.** 한 문장이고 카드에서 두 줄을 넘지 않는다(약 45자).
- 더 읽기의 나머지와 확인 질문의 글은 뜻을 바꾸지 않는다.
- 검수는 2026-10-25 설계 7장을 따른다. 다 쓰면 `korean-humanizer`로 다듬고, 별도 리뷰어(opus)가 사실을 대조하고, 사용자가 읽는다. `steps.ts`의 `label`과 `line`도 검수 대상이다.

3단계의 동작 줄 초안이다. 시안에 실었던 문장이고 `look`은 설계자가 채웠다. 확정은 검수에서 한다. 다른 단계는 쓰는 사람이 정한다.

| 동작 | `line` | `look` |
|---|---|---|
| bgeu 실행 | `` `a0`이 `a1` 이상이면 반복을 빠져나간다. `` | 실행 줄 |
| sw 실행 | `` `a0`이 가리키는 곳에 0을 쓴다. `` | 실행 줄 |
| addi 실행 | `` `a0`을 4 올린다. `` | 레지스터 `a0` |
| j 실행 | 맨 위로 돌아간다. | 실행 줄 |
| 한 바퀴 더 | 네 줄을 한 번에 돈다. | 레지스터 `a0` |

## 7. 디자인 진행 (design-flow)

- 화면 구조 방향은 이 문서 3·4장으로 정했다. brainstorming 대화의 비주얼 컴패니언 와이어프레임을 사용자가 보고 골랐다.
- `impeccable shape`는 `PRODUCT.md` init을 먼저 요구해 돌리지 않았다. `PRODUCT.md`는 만들지 않았다(설계자 판단, 사용자에게 알림).
- 구현 태스크마다 design-flow 5단계 브리프를 싣는다. DS 규칙은 `apps/web/node_modules/@eeennsu/web/README.md`의 `## 소비 규칙`(0.5.0)이다.
- 계획서 마지막 태스크는 "디자인 마무리"(다듬기 → 모션 → 비평·감사 → 실제 화면 확인 → 마무리 검사 → 기록)이고 메인 세션이 돌린다. 세션은 `apps/web`에서 연다(훅이 처음 만나는 `package.json`만 본다).
- 시안의 색·글꼴·간격은 DS가 아니다. 배치와 구성만 따른다.

## 8. 검토한 방법

**왼쪽 열**

| 방법 | 내용 | 판단 |
|---|---|---|
| A. 표를 canvas 옆으로 | canvas 옆 376x480 칸에 실행 줄과 탭. 모든 장이 한 배치 | 터미널을 40열로 줄이고 메모리 표를 8바이트 줄로 바꿔야 한다. `a2` 줄이 첫 화면 경계(y901~938)에 걸리고 빈 canvas가 그대로다. 기각 |
| **B. 위 띠** | canvas를 줄여 터미널 옆에, 표를 4쌍으로 | 표 전체가 첫 화면에 든다. canvas를 쓰는 장에는 다른 배치가 필요하다. **선택** |
| C. 지금 순서 유지 | 바뀐 값은 카드에서만 | "표에서 그 값이 있는 줄" 기준을 포기한다. 기각 |

**카드**

| 방법 | 내용 | 판단 |
|---|---|---|
| **K1. 목록, 지금 것만 펼침** | 이름은 다, 설명·값은 방금 것과 다음 것만 | 읽기·누르기·값 보기가 한 묶음으로 내려간다. **선택** |
| K2. 한 번에 하나 | 다음 버튼과 방금 값 표만 | 가장 짧지만 반복의 모양이 안 보이고 지난 설명을 다시 못 본다. 기각 |
| K3. 전부 펼침 | 모든 설명이 처음부터, 값이 기록으로 | 가장 길고 방금 값이 묻힌다. 기각 |

| 방법 | 내용 | 판단 |

| 3. 동작 데이터까지 MDX | | 실행기와 테스트가 렌더 전에 동작을 읽어야 한다. 기각 |

## 9. 성공 기준

- 1900x940에서 2장의 다섯 단계 모두, 더 읽기를 접고 스크롤을 맨 위에 둔 채 각 동작을 차례로 누를 때: 다음 버튼, 방금 한 동작의 값 표, 그 동작의 "볼 곳"(레지스터 줄, 메모리의 강조된 바이트, 실행 줄, 터미널)이 뷰포트 안에 있다. agent-browser로 좌표를 재서 확인한다. 넘으면 4장 "카드가 첫 화면을 넘을 때"를 따른다.
- 1900x940에서 2장의 레지스터 표 전체가 첫 화면 안에 있다.
- 1440x900에서도 같은 것을 재서 결과를 보고한다. 통과 기준은 아니다(사용자가 정한 기준 화면은 1900x940이다).
- 탭을 바꾸거나 동작을 눌러도 에뮬레이터가 다시 켜지지 않는다.
- 다섯 단계의 본문이 세 문장 이하이고, 어디를 보라거나 버튼이 무엇을 한다는 문장이 본문에 없다.
- `pnpm typecheck` · `lint` · `format:check` · `test` · `build:plugin` · `smoke:plugin` · `e2e`가 통과한다. design-flow 마무리 검사가 0건이다.
- 고쳐 쓴 글이 사실 대조와 사용자 읽기를 거쳤다.
- 놀이터가 지금과 같이 동작한다.

## 10. 빌더에게 맡기는 것

- 4쌍과 2쌍을 가르는 방식(CSS로 둘 중 하나를 숨기기, 미디어 쿼리 훅 등)과 정확한 경계.
- 줄인 canvas의 정확한 크기와 띠의 간격(DS 스케일 안에서).
- "볼 곳"과 "외 n개"의 문구, 값 표의 모양(design-flow 다듬기). 문구는 사용자 읽기에서 확인받는다.
- `look.fields` 키의 타입 표기와 `StepList` 안 컴포넌트 나누기.
- `resultText`·`hintText`를 대신할 순수 함수의 이름과 위치, `tryText.test.ts`를 어떻게 바꿀지. 값 표의 줄을 만드는 로직(앞 값 없음, `setRegister`, 외 n개)에는 테스트를 둔다.
- 코드 컨벤션은 conventions 스킬을 따른다(레포 `CLAUDE.md`).

## 11. 미확인

- 4쌍 레지스터 표의 실제 폭과 높이. 3장의 좌표(표 위 y442, 바닥 y849, `a0` 줄 y627 부근)는 실측 크기로 계산한 값이다.
- K1 카드의 실제 높이. 시안은 DS 글꼴·간격이 아니다.
- 1440x900은 열 폭이 1900x940과 같지만 높이가 40px 낮다. 왼쪽 표는 들어간다고 계산했고(바닥 y849), 오른쪽 카드는 모른다. 그보다 낮은 화면(예: 1280x720)은 재지 않는다.
- 4·5단계의 지금 좌표는 재지 않았다.
- 2장 밖에서 어느 장이 `'small'`인지. 상위 설계의 챕터 표로는 0~3장과 6장이 화면을 안 쓰는 것으로 보이지만 정한 것이 아니다.
